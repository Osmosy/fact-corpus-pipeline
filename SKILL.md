# Конвейер фактов: колода → факты → модели → сравнение → выводы

## Overview

Аналитика корпуса (колоды, отчёты, исследования) делается в восемь шагов, и каждый шаг
пишет артефакт, а не «понимание в голове»: материал → машиночитаемые факты → анализ
несколькими моделями → сравнение → разбор слепых зон → решения → реестр обязательств →
итоговый документ.

Смысл не в том, чтобы «прогнать LLM по документам». Смысл в том, что после прогона
видно конкретно: какие факты модели взяли в опору, на чём они сошлись, что не взял никто,
и каких признанных обязательств в выводах нет. «Выводы выглядят полными» заменяется
числом.

Ключевая развилка, которую нужно держать в голове: **факт ≠ требование**. Факт —
размеченный материал, из которого выбирают. Требование — обязательство, которое проверяется
предикатом. Смешать их значит либо превратить весь корпус в вечный блокирующий долг, либо
потерять контроль над полнотой.

## When to Use

- Есть корпус (презентации, отчёты, PDF) и вопрос, на который нужны обоснованные выводы.
- Нужно сравнить, что разные модели сочли важным, и собрать итоговый документ.
- Нужно доказать полноту выводов, а не заявить её.
- Нужно повторить ту же аналитику на новом корпусе без сборки инструментов заново.

Не для: одиночного вопроса по одному файлу (хватит чтения), перевода/реферирования без
проверки чисел, задач, где нет первоисточника с координатами (страница/строка).

## Этап 0. Качество входа — до любого анализа

Половина ошибок в этой работе рождается не в моделях, а в материале: склеенные панели,
повторы слайдов, обрезанные ячейки, растр, прочитанный «по смыслу». Дешевле проверить
вход, чем ловить это в выводах.

Что должно быть в разметке колоды:

- страница начинается с `## Слайд N — <заголовок>` (атомизатор ищет именно этот якорь);
- панели помечены `### РФ` / `### РБ` и не смешаны в одной таблице;
- каждая таблица — markdown-строки `| … | … |`, без объединённых ячеек;
- растр (диаграмма) прочитан по рендеру и помечен комментарием автора колоды.

Чек-лист входа (проверяется командами, а не глазами):

1. **Число на странице.** Для каждого извлечённого числа — дословный поиск на его странице:
   `audit-checks.py`-подобная сверка даёт «число есть на цитируемой странице» для 89 из 91
   проверки; остаток разбирается по существу, а не списывается.
2. **Подпись — подстрока строки.** Подпись факта обязана быть дословной подстрокой строки
   таблицы. Склейка вида «РБ — 2-3 раза в неделю» это первое, что делает модель, если не
   потребовать обратного; после требования «ровно как в строке» — 16 из 16 и 397 из 398
   на корпусе.
3. **Панель не пересекается.** У одинаковых строк в панелях РФ и РБ разные числа; при
   регистрации требования панель определяется по ближайшему заголовку `###`, иначе
   белорусская строка уедет в выводы по рынку РФ.
4. **Повторы слайдов.** Ищи в заголовке `повтор слайда` — такие страницы дублируют факты
   предыдущей (в корпусе нашёлся слайд 45 = «повтор слайда 44»), и требования начинают
   ссылаться на копию.
5. **Обрезанные ячейки.** Многоточие в ячейке (`…`) означает, что текст в колоде уже
   урезан: подпись получится неполной, и последующий поиск в выводах будет врать.

Правило входа: сомнительное число не «додумывается», а попадает в `*-rejected.jsonl` с
причиной. Отклонённый факт виден; выдуманный — нет.

## Этап 1. Атомизация: страницы → факты

`page_facts.json` — по колодам и страницам: `{deck_sha256, extracted_by, pages: {N: {note, facts: [{label, value, verified}]}}}`.
Каждый факт обязан иметь `verified: true`; отклонённые идут в отдельный журнал.

Затем канон: `docs/facts/facts.jsonl`, одна строка на факт.

```json
{"fact_id": "F-1a2b3c4d5e6f", "deck": "inkofood-2026", "page": 34,
 "label": "Дата производства и срок годности на лицевой стороне упаковки",
 "value": "61,7 %", "thematic": true, "deck_sha256": "…"}
```

`fact_id` = sha256 от `(deck, page, label, value)`, первые 12 hex. Почему так: id не зависит
от порядка вставки, повторная сборка не сдвигает номера и не плодит дублей при добавлении
новых колод. Ссылки вида «F-» переживают пересборку.

Проверки канона: уникальность id, `label` и `value` непустые, `page` резолвится в спан,
`thematic` считается по словарю темы (мяс/колбас/упаковк/состав/покуп/цен/…), а не на глаз.

## Этап 2. Анализ моделями

Контракт ответа — строгий JSON, и только он идёт в сравнение:

```json
{"selected":    [{"fact_id": "F-…", "why": "чем важен"}],
 "conclusions": [{"text": "вывод", "fact_ids": ["F-…"]}],
 "not_relevant":[{"fact_id": "F-…", "why": "почему не значим"}]}
```

Приёмка прогона: все `fact_id` существуют в каноне; выводы есть; у каждого вывода есть
ссылки. Иначе прогон сохраняется с `problems` и в сравнение не идёт. На корпусе это дало
14 принятых прогонов из 14 — то есть проверка не формальность, а фильтр, который обычно
срабатывает на первом прогоне нового типа документа.

Практика прогона:

- промпт = вопрос исследования + строки `id | стр. | подпись | значение` + контракт;
- крупный промпт (209 фактов, 14 тыс. символов) проходит штатно: ~79 тыс. токенов и ~6 минут;
- батчи по 5–6 нужны для десятков независимых запросов, а не для одного большого;
- каждый прогон пишется в `runs/<колода>.<backend>-<штамп>.json` вместе с `usage` и `sessionId`.

Каналы взаимозаменяемы: CLI с промо-пулом (см. `zcode-start-plan-cli`, ответ лежит внутри
конверта `sessionId/response`) и OpenAI-совместимый шлюз к облачной модели. Стоимость
известна: один прогон колоды ≈ 2 млн единиц пула; весь корпус из 7 колод — 27,6 млн.

## Этап 3. Сравнение

Сравнение — не вычитание. Четыре среза выбора фактов:

- **выбрали все** — костяк итогового документа;
- **большинство** — рабочая зона;
- **ровно один** — повод проверить, не пропуск ли это (на корпусе 105 таких фактов);
- **не выбрал никто** — слепые зоны, отдельный проход.

Выводы кластеризуются по пересечению `fact_ids` и по близости текста (difflib, порог 0.55):
одинаковые по смыслу формулировки собираются, разные не склеиваются. Результат: на корпусе
52 кластера выводов, из них 30 сформулировали обе модели.

При одном прогоне сравнение вырождено — это надо писать в документе, а не оставлять
читателю догадываться, почему «согласны все» и «только у одного» совпали.

## Этап 4. Слепые зоны (второй проход)

Факты, которые не взял никто, отдаются моделям отдельным вопросом: `material` /
`background` / `irrelevant`, с причиной и обязательным вердиктом на каждый id.

Зачем отдельный проход: массовый прогон теряет факты на внимании, а не на значимости.
На корпусе 43 слепых зоны распались на 9 настоящих потерь, 6 расхождений и 28 фонов — то
есть «не взяли 24 % корпуса» оказалось в основном не потерей, и это удалось показать только
вторым проходом.

## Этап 5. Решения: три судьбы факта

У каждого спорного факта появляется записанное решение:

- `conclusions` — факт обязан быть в выводах (проверяется в текстах выводов);
- `info` — факт идёт в приложение «Справочно», в выводы не обязан (проверяется только там);
- `waive` — обязательство снимается с причиной и перестаёт блокировать приёмку.

Носители: `fact_decisions.json` (по факту, с причиной), `dispositions.json` (в терминах
требований), `build_appendix.py` — единственный генератор приложения. Второй генератор
приложения обязателен к удалению: два скрипта дают две разные версии документа.

Правило, без которого «справочно» превращается в свалку: в приложении у каждого факта
стоит колода, страница, число и причина. Тогда «обозначили для информации» проверяемо:
предикат ищет факт именно в приложении, и удаление строки ломает гейт.

## Этап 6. Реестр обязательств и гейты

Механика реестра (спаны, байтовые хэши, append-only, коды выхода) — в навыке
`requirements-registry`. Здесь только то, как он встраивается в конвейер:

- требование опирается на спан строки таблицы (`--split rows`), а не на страницу: иначе
  несколько требований с одной страницы делят один `raw_text` и реестр не различает,
  какое доказано;
- предикат обязательства — не «число есть в колоде» (это докажет любая страница), а «факт
  учтён там, куда его положили решением»;
- у каждого доказательства записан опровергатель: чем факт был бы снят;
- приёмка — перезапуск чекера (`replay`), а не чтение лога;
- покрытие и дрейф считаются раздельно: `coverage` — про вердикты по спанам, `drift` — про
  живые обязательства без доказательств.

Красный `drift` — это состояние работы, а не поломка реестра. На корпусе он держит 19
обязательств, которых нет в выводах, и это ровно тот список, который нельзя закрыть кодом.

## Запуск на новом корпусе

1. Колоды → markdown с якорями `## Слайд N` и панелями; прогнать чек-лист этапа 0.
2. `build_facts.py` → `facts.jsonl`; проверить уникальность id и число тематических.
3. `run_analysis.py --backend <канал> --deck <колода>` на каждую колоду и каждый канал.
4. `compare_analyses.py <колода>`; при двух и более прогонах — читать срезы.
5. `summary_all.py` — картина по корпусу.
6. `blind_spots.py` → `--review <канал>` → `--summary`.
7. Решения: `apply_fact_decisions.py`, `rb_to_info.py` (если есть второстепенный рынок),
   `build_appendix.py`, `apply_dispositions.py`.
8. Гейты: `coverage`, `drift`, `replay`; цифры — в README, а не в переписке.

## Скрипты навыка

Скрипты лежат в `scripts/` этого навыка, проект хранит только данные. Корень проекта
берётся из переменной `CORPUS_ROOT`, поэтому один и тот же скрипт работает на любом корпусе:

```bash
SKILL=~/.hermes/skills/research/fact-corpus-pipeline/scripts
cd /path/to/project
CORPUS_ROOT=$PWD python3 $SKILL/build_facts.py
CORPUS_ROOT=$PWD python3 $SKILL/run_analysis.py --backend zcode --deck <колода>
CORPUS_ROOT=$PWD python3 $SKILL/compare_analyses.py <колода>
CORPUS_ROOT=$PWD python3 $SKILL/summary_all.py
CORPUS_ROOT=$PWD python3 $SKILL/blind_spots.py --review zcode
CORPUS_ROOT=$PWD python3 $SKILL/blind_spots.py --summary
CORPUS_ROOT=$PWD python3 $SKILL/apply_fact_decisions.py   # читает docs/facts/plan.json
CORPUS_ROOT=$PWD python3 $SKILL/build_appendix.py
CORPUS_ROOT=$PWD python3 $SKILL/apply_dispositions.py    # нужен GRACE_REGISTRY
```

| скрипт | что делает | где данные проекта |
|---|---|---|
| `build_facts.py` | `page_facts.json` → `facts.jsonl` | `docs/facts/` |
| `run_analysis.py` | прогон модели, валидация контракта | `docs/facts/runs/` |
| `compare_analyses.py` | четыре среза + кластеры выводов | `COMPARISON-<колода>.md/json` |
| `summary_all.py` | картина по корпусу | `SUMMARY.md` |
| `blind_spots.py` | список слепых зон и второй проход | `BLIND-SPOTS*.md/json` |
| `apply_fact_decisions.py` | план → `fact_decisions.json` + `dispositions.json` | `docs/facts/plan.json` |
| `build_appendix.py` | единственный генератор приложения «Справочно» | `reviews/*/APPENDIX-INFO.md` |
| `apply_dispositions.py` | применяет решения к реестру | `docs/registry/dispositions.json` |
| `rb_to_info.py` | панель второстепенного рынка → справочно | `--panel`, `--reason` |
| `run_all.sh` | все колоды × все каналы | `DECKS`, `BACKENDS` |

Переменные: `CORPUS_ROOT` — корень проекта, `APPENDIX_INFO` — путь к приложению (по
умолчанию единственное `reviews/*/APPENDIX-INFO.md`), `GRACE_REGISTRY` — путь к
установленному реестру (по умолчанию `~/projects/vector-grace/registry`).

План решений — данные проекта (`docs/facts/plan.json`, формат `{fact_id: [target, reason]}`),
а не константа скрипта: решения меняются по ходу работы, а скрипт должен оставаться общим
для всех корпусов.

`dispositions.py` живёт в проекте (`docs/registry/tools/`), потому что его импортирует
предикат `check_fact_in_conclusions.py`; в навыке его копия нужна для `apply_dispositions.py`.
Если правила диспозиций меняются — правятся оба, иначе чекер и применитель разойдутся.

## Common Pitfalls

- **Модель склеивает подписи панелей** («РБ — 2-3 раза в неделю»): в промпте требовать
  «подпись — дословная подстрока строки», а на приёмке сверять подпись машинно. Без этого
  первый прогон даёт 2 из 16.
- **Поиск ответа по первому JSON в stdout** ловит конверт CLI (`sessionId`, `response`) и
  даёт нули при потраченных токенах: сначала снимать конверт по `sessionId`, потом
  разбирать `response`.
- **Разбор ответа по одному ключу** (`selected`) ломает второй тип вопроса (вердикты по
  слепым зонам идут ключом `verdicts`): извлекатель должен принимать набор ключей.
- **Сравнение по номеру страницы и числу** даёт тавтологию и ложные совпадения («6,6» стоит
  на трёх страницах): сопоставлять по подписям (нормализация, основы слов, difflib), а не
  по числам.
- **Правка чекера после регистрации** инвалидирует все его доказательства: `replay`
  отказывает с кодом 3. Условия и правила держать в данных (`falsifiers.json`,
  `dispositions.json`), сам чекер доводить до регистрации и не трогать; при неизбежной
  правке — перевыпускать инварианты с новой версией.
- **Пути прибиты к одному проекту** (`Path.home()/"projects/<имя>"`) — скрипт умирает на
  втором корпусе: корень берётся из `CORPUS_ROOT`, а план решений — из `plan.json` проекта.
- **Пересборка диспозиций затирает решения требований-двойников.** Две строки с одинаковым
  `raw_text` дают два требования, а обратное отображение по тексту возвращает одно — второе
  теряет решение, и `replay` падает на нём. Отображение «текст → список требований», а
  прежние диспозиции сливаются с новыми, а не заменяются.
- **Дубли требований по тексту** не всегда дубли: три требования могут законно делить один
  спан (три прочтения одного абзаца). Снимать дубль можно только когда совпадает и спан,
  и смысл; иначе получишь `orphaned_evidence` и рост блокирующих находок.
- **Возврат из `superseded` в живой статус** без снятия `superseded_by` залипает в мёртвом
  статусе — инструмент обязан чистить указатель, тест на это нужен.
- **Приложение «Справочно» из двух генераторов** расходится по версиям: один генератор,
  остальные вызывают его.
- **Второстепенный рынок смешивается с целевым.** Если цель — один рынок, второй уходит в
  `info` правилом (например «РБ → справочно»), а не выбрасывается: факты остаются, но не
  блокируют выводы и не подменяют числа целевого рынка.
- **Предикат «факт в выводах» ищет дословную подпись** и даёт ложный провал на пересказе
  («больше мяса» вместо «высокое содержание мяса»). Это лечится сопоставлением по основам
  слов, а не ослаблением проверки; до тех пор ложные провалы честно называть ложными.

## Verification Checklist

- [ ] Каждый факт канона: `label` — подстрока строки колоды, `value` найден на его странице,
      `fact_id` уникален (`python3 docs/facts/build_facts.py` печатает 0 дублей)
- [ ] Панели не пересечены: у требований про РФ в спане нет заголовка `### РБ`
- [ ] Все прогоны приняты: `problems` пуст у каждого файла в `runs/`
- [ ] Сравнение показывает четыре среза и число кластеров; при одном прогоне стоит пометка
      о вырожденности
- [ ] Слепые зоны имеют вердикт на каждый факт (`--summary` печатает 0 без вердикта)
- [ ] Каждое решение в `fact_decisions.json` несёт причину и колоду/страницу
- [ ] `APPENDIX-INFO.md` собирается `build_appendix.py`, число строк равно числу `info`
- [ ] `coverage` чист, `replay` совпадает по всем доказательствам, `drift` печатает только
      те обязательства, которых действительно нет в выводах
- [ ] Цифры из гейтов перенесены в README репозитория, а не остались в переписке
